# Integración incremental y recuperación
Usar el coordinador existente, no otro tracker. Antes de empezar resolver la política efectiva del Home y de cada repositorio; no inferir permiso de push/merge de una skill. Un agente puede terminar localmente y entregar una referencia conservada en su host. El integrador debe poder observarla o recuperar su ubicación autorizada; no inventar disponibilidad entre máquinas. No borrar la última ref hasta observar el destino y dependientes.

CLI multi_agent_cli.py usa claim normal, deliver --candidate-file ... --product-repo ... --resources-clear --evidence-ref ...; adopt --product-repo ... --resource repo://... --lease-until ... --harness ...; complete --assessment-file ... --product-repo ... --target-remote origin --terminal-status ... --resources-clear --evidence-ref ... . En cada operación usar autoridad, task, actor, claimId, generation y eventId estable. Al adoptar un commit ya integrado usar --target-remote. Complete exige exactitud del candidato y del commit remoto (git ls-remote y merge-base en el checkout, sin fetch automático); si no existe localmente la revisión remota, refrescar de forma autorizada. Solo merge/fast-forward con ancestralidad: squash/rebase necesita un protocolo de equivalencia explícito, no se infiere. El scope del checkout y remoto lo verifica el host; el helper no autentica revisor ni otorga permisos. El coordinador no hace merge o push de producto por su cuenta.

Assessment: proyección delivery-assessment del verificador autorizado, con contractDigest (del candidato), candidateCommit, targetCommit, targetRef, generation, scope, taskId y observationDigest además de contadores y status CANDIDATE_READY. Contrastar cada evidencia primaria y repetir solo garantías afectadas; no construir PASS a partir de un git merge-base. La estructura no certifica el consumidor. Integración y cierre multi-repo no son transacción; si hay interrupción, observar target antes de repetir efectos. Un error de push Home es indeterminado, reintentar con mismo eventId. Si hay cambio semántico, detener y reconciliar contrato. No editar Done directamente si el claim está activo.

El scheduler devuelve integrationCandidates y pendingIntegrations. Configurar opcionalmente maxPendingIntegrations y repositories por taskId para reducir deuda en la cadena; independiente sigue adelante. Priorizar candidatos que desbloquean trabajo; no implementar de nuevo. Handoff por tarea/intento y evidencia fuera de Git si contiene datos privados. No reemplazar el Steward administrativo por un segundo scheduler. El supervisor conserva responsabilidad de integración.
