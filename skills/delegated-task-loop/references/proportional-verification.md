# Verificación proporcional y alcance publicado

Supervisor: leer resultado, contrastar revisión real, AC/DoD, higiene y cambios con el plan delivery-first-testing. Validar procedencia, argv/selectores y resultados originales. Reejecutar únicamente oráculo decisivo asignado o evidencia inválida; no volver a ejecutar toda la batería del worker. Obligaciones reales de integración/publicación intactas. Si plan cambia, emitir amendment. No declarar PASS por inspectar texto ni forzar un cambio de comportamiento para satisfacer prueba ajena.

Antes de delegar, snapshot de HEAD/rama/worktree, refs locales y remotas reales, permisos y rutas autorizadas en cada repo tocado. Usar git status --porcelain, git log BASE..HEAD, git diff --name-status y git for-each-ref; consultar cada remoto autorizado con git ls-remote --refs (no usar solo origin/main cacheado). Atribuir ref al repositorio+remoto correcto, no incluir URLs con credenciales ni publicar snapshots. Si varios remotos, una entrada identificada por repo+remote y lista completa. Guardar snapshots privados. Antes de aceptar, obtener de nuevo observaciones. publication_audit.py recibe publication-audit-input v1 por stdin, repositories [{id,baseline:{local,remote},after:{local,remote},allowedLocalRefs,allowedRemoteRefs,evidenceRef}]. Los maps son ref→SHA completo, remote null si no disponible. Las excepciones son refs exactas autorizadas. Refs nuevas, borradas o cambiadas no autorizadas → INVESTIGATE; ausencia de evidencia remota UNKNOWN. No detectar pushes revertidos solo por snapshot; consultar eventos de proveedor cuando necesario. No afirmar autoría de cambios por coincidencia temporal; no hacer rollback/delete automático. Comprobar diff/path scope y worktree independientemente. Preferir permisos efectivos que impidan publicación.

## Frontera de entrega
Fijar deliveryTarget en el brief: scope (research/internal/integration/product-capability/release), targetRef, authorityRef, consumerJourney [{id,statement,checkId}]. Un paso público debe referir un supervisorCheck real. No usar fixtures que eludan el punto de entrada ni sustituir clientes exigidos. El supervisor contrasta el artefacto objetivo y cada AC/DoD original con evidencia primaria vigente; una referencia de worker no basta. Si cambia la revisión tras merge, revalidar lo afectado.

Tras READY_FOR_REVIEW, ejecutar `python3 scripts/delegation_contract.py accept ENVELOPE RESULT OBSERVATION`. La observación v2 usa identidad y briefRevision/briefDigest, resultDigest, taskDigest, reviewerRef, targetRef, targetEvidence, criteria por ID y journey por ID. Cada comprobación es {status: PASS/FAIL/BLOCKED/NOT_RUN, evidenceRefs: [...]}. CANDIDATE_READY es coherencia estructural, no autenticación ni aprobación. Reconciliar el contrato original con la tarea actual y comprobar fuentes antes del cierre vía Backlog. Los briefs antiguos sin deliveryTarget pueden leerse, no acreditan cierre. No crear otro registro de trabajo.

## Proyección automática de observaciones de integración
Para un repo, deliveryTarget.integration={repository,contractDigest} fija el contrato semántico observado por el coordinador antes de delegar. El host autorizado entrega observaciones de sus checks planificados por ID, repositorio y SHA del destino; no ejecutar argv desde un resultado del worker. `delegation_contract.py project-acceptance ENVELOPE RESULT CHECKS` combina las observaciones en el assessment consumido por complete. CHECKS es acceptance-check-observations v2 con identidad/briefRevision/briefDigest/resultDigest, reviewerRef, targetEvidence, integration={contractDigest,candidateCommit,targetCommit,generation}, checkResults [{id,repository,revision,status,evidenceRefs}]. Ausentes = NOT_RUN; otro SHA se rechaza; FAIL y BLOCKED prevalecen. El candidato se contrasta con el resultado original. La observación del destino debe proceder del host, no de un fixture de tests. No se autentica al productor ni se atribuye una ejecución real por estructura. Multi-repo exige pins explícitos y revisión manual hasta disponer de adaptador.
